# Supabase backend

Финатлон использует [Supabase](https://supabase.com) как бэкенд: авторизация,
Postgres, REST API и RLS. Своего сервера на Node не требуется.

## Структура папок

- `src/shared/supabase/` — supabase-клиент и типы `Database`.
- `src/shared/api/` — сервисный слой (`news`, `programs`, `partners`, ...).
- `src/shared/auth/` — `AuthProvider`, `useAuth`, обёртки `signIn` / `signUp` / `reset`.
- `supabase/migrations/` — SQL-миграции схемы.
- `.env.local` — URL и публичный ключ (в git не попадает).

## Таблицы

Приватные (видят только владельцы; админ — всё):

- `profiles` — расширение `auth.users` (имя, телефон, дата рождения, город,
  школа/ВУЗ, соцсети, биография, флаг `is_complete`, роль `user|admin`).
- `user_events` — история участия пользователя в мероприятиях.
- `achievements` — достижения пользователя (выдаются админом).
- `notifications` — личные уведомления (массовая рассылка — из админки).
- `olympiad_registrations` — регистрация участника на профиль олимпиады
  (одна строка на пару «кабинет + профиль», анкета на момент отправки —
  в `form_data`). Создаётся только функцией `register_for_olympiad_profile`.

Поля полной регистрационной анкеты (адрес, образовательное учреждение,
родитель, учитель и т. д.) хранятся в `profiles`.

Контент (публичное чтение, запись — только админ):

- `news` — новости (slug, заголовок, текст, обложка, статус публикации).
- `programs` — карточки направлений на главной (Викторина / Олимпиада / Форум).
- `timeline_events` — события для таймлайна.
- `stats` — числовые метрики «5+ тыс школьников», «100+ ВУЗов».
- `partners` — партнёры и организаторы (поле `kind`).
- `council_members` — попечительский совет.
- `documents` — документы с категориями.
- `faqs` — часто задаваемые вопросы.
- `site_settings` — глобальные тексты (hero, about, контакты).
- `olympiads` — олимпиады, формат, сроки, публикация и состояние регистрации.
- `olympiad_profiles` — приватные профили участия, баллы и дипломы; запись только администратором.

Все таблицы защищены RLS. Политики используют функцию `is_admin(uid)`, которая
проверяет роль через таблицу `profiles`.

## Как развернуть БД

### Существующий проект: сначала проверьте историю

`20260514000000_init_schema.sql` удаляет таблицы. **Никогда не запускайте эту
миграцию повторно на действующей базе** и не используйте `db reset --linked`.
`npm run db:reset` сбрасывает только локальную тестовую базу.

После входа через `npm run db:login` и привязки проекта проверьте
`npx supabase migration list` и `npx supabase db push --dry-run`. Если CLI предлагает
запустить начальную миграцию на существующей базе, остановитесь и сверяйте историю
с реально применённой схемой; не отмечайте неизвестные миграции как применённые.

Для базы с уже существующими `olympiads` и `olympiad_profiles` подготовлена отдельная
миграция `20261117000000_harden_olympiads.sql`. Она добавляет `format` и
`registration_open`, сохраняет старый `stage` и данные, ограничивает публичное
чтение опубликованными олимпиадами и защищает изменение роли пользователя.
Не применяйте вместе с ней старые миграции повторно. До обновления новый раздел
админки работает только на чтение; главная совместима со старой схемой.

Ограничения данных добавлены как `NOT VALID`: новые записи и обновления проверяются,
исторические записи не исправляются автоматически. Проверять и валидировать их
следует отдельно после аудита данных. Примерные олимпиады в production не создаются.

### Новый пустой проект

```bash
npm run db:login
npm run db:link
npx supabase db push --dry-run
npm run db:push
```

Для локальных проверок SQL и RLS без доступа к production используется
`npm run test:unit` (изолированный PostgreSQL через PGlite). Это не заменяет
проверку схемы и доступа после применения миграции в Supabase.

## Включение Email-провайдера

В **Authentication → Providers → Email**:

- Email включён по умолчанию.
- Для разработки выключите **Confirm email**, чтобы пользователи могли
  логиниться сразу после регистрации.

## Как назначить администратора

После регистрации обычного аккаунта (через сайт) откройте Supabase Studio →
**Table Editor → profiles**, найдите свою запись и поменяйте поле `role` с
`user` на `admin`. После следующего логина у вас появится доступ к `/admin`.

Альтернативно через SQL Editor:

```sql
update public.profiles
set role = 'admin'
where email = 'you@example.com';
```

## Деплой

1. Залейте репозиторий на GitHub.
2. На Vercel → **Add New Project** → выберите репо.
3. В **Environment Variables** добавьте `VITE_SUPABASE_URL` и
   `VITE_SUPABASE_KEY` из `.env.local`.
4. **Deploy** — Vercel соберёт и выдаст ссылку.
